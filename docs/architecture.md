# Architecture

## The pieces

| Piece | Role |
|---|---|
| [firstmate](https://github.com/kunchenguid/firstmate) | An "agent distro": a git checkout of instructions, skills and scripts that turns a coding agent into a supervisor. You talk to that agent (the first mate); it spawns, supervises and reports on a crew of worker agents. |
| [Orca](https://github.com/stablyai/orca) | Owns each worker's git worktree and terminal. Runs headless on the VPS (`orca-ide serve`); the Orca app on your Mac or phone is just a client. |
| Pi | The `personal` harness. Uses GPT-5.6 models through the ChatGPT subscription (`openai-codex` provider). |
| Claude Code | The `work` harness. Uses Claude Opus 5.5 and Fable 5.1. |
| NixOS + this flake | Declares the whole machine and pins every version. |
| Tailscale | Private network between the VPS and your devices. Orca is only reachable through it. |

## How a request flows

```
 you ──ssh──▶ personal@vps ──▶ tmux "firstmate" ──▶ pi (first mate)
                                                       │ fm-spawn (backend=orca)
                                                       ▼
                                   orca-serve-personal (port 6768)
                                     ├─ worktree + terminal ─▶ pi worker  (Terra/Sol)
                                     ├─ worktree + terminal ─▶ pi worker
                                     └─ ...
                                                       ▲
 Orca app on Mac/phone ──tailnet──────────────────────┘  (watch, type into terminals)
```

The `work` context is the same picture with the `work` user, Claude Code and port 6769.

1. You SSH in as a context user and run `fleet`, which attaches to a tmux session running that context's harness inside the firstmate checkout.
2. You ask the first mate for something. It writes a brief and calls firstmate's spawn script with `backend=orca` (from `config/backend`).
3. The spawn script asks the local Orca server, through the `orca` CLI, to create a worktree and a terminal, then launches a worker harness in it. Which model and effort the worker gets comes from `config/crew-dispatch.json` (see [configuration](configuration.md#model-routing)).
4. The first mate supervises the crew and reports back with PRs, merges or investigation reports.
5. Meanwhile, the Orca app on your devices shows every worker's terminal live.

## Why one Linux user per context

Orca's documentation is explicit: remote sessions use the **server's** `PATH`, home directory and credentials. Workers inherit the Orca server's environment, not the environment of the shell that asked for them.

So per-context separation through environment variables (a different `GH_CONFIG_DIR`, `CLAUDE_CONFIG_DIR` or git identity per tmux session) would never reach the workers. Instead, each context is a separate Linux user running its own Orca server:

| Isolated per user | Where |
|---|---|
| GitHub account | `~/.config/gh` |
| Git identity | `~/.gitconfig` |
| Claude or Pi login | `~/.claude`, `~/.pi/agent` |
| firstmate state, backlog, memory, project clones | `~/fleet/firstmate/{data,state,projects}` |
| Orca projects, worktrees, terminals | that user's Orca server |

No environment juggling, and a mistake in one context cannot touch the other's credentials.

## What runs on the machine

Per context (`<ctx>` is `personal` or `work`):

| Unit | Type | Does |
|---|---|---|
| `fleet-setup-<ctx>` | oneshot, as the user | Clones firstmate at the pinned commit, copies `homes/<ctx>/config/` into it, writes `pi-account` for Pi contexts, and lets firstmate install its own toolchain. Reruns when the repo or the firstmate pin changes. |
| `orca-serve-<ctx>` | long-running, as the user | Waits for the Tailscale IP, then runs `orca-ide serve --port <port> --pairing-address <tailscale ip>`. Logs to `/var/log/fleet/orca-<ctx>.log`. Not restarted by rebuilds. |

Machine-wide: `sshd`, `tailscaled`, the firewall, `nix-ld`, weekly Nix garbage collection, and (first boot only) `fleet-bootstrap`.

## Where things live

| Path | Contents | Source |
|---|---|---|
| `/etc/nixos/flake.nix` | The machine's flake. Pulls this repo as the `fleet` input. | Generated by `install.sh` |
| `/etc/nixos/configuration.nix` | Disk, boot, network, root's SSH keys | Generated by nixos-infect |
| `/etc/nixos/fleet.nix` | Enabled contexts, SSH keys, Tailscale key path | Generated by `install.sh` |
| `/etc/nixos/secrets/ts-authkey` | Tailscale auth key (mode 600) | `install.sh` |
| `/etc/fleet/contexts.json` | Context list read by the `fleet` command | The module |
| `/home/<ctx>/fleet/firstmate/` | firstmate checkout and firstmate home | `fleet-setup-<ctx>` |
| `/var/log/fleet/orca-<ctx>.log` | Orca server log, including the pairing link (mode 600) | `orca-serve-<ctx>` |

## Version pinning

| What | Pinned by |
|---|---|
| NixOS, system packages | `nixpkgs` in `flake.lock` |
| Orca, Pi, Claude Code | `llm-agents` in `flake.lock` |
| firstmate | `firstmate` in `flake.lock` (cloned per user at that commit) |
| nixos-infect | Commit hard-coded in `install.sh` |
| `no-mistakes`, `*-axi` tools | **Not pinned.** Installed by firstmate at runtime. |

The machine's own `/etc/nixos/flake.lock` records which commit of this repo it runs. `fleet-rebuild` moves it to the latest commit.

## Security model

- **Network.** Only SSH (port 22) is open to the internet, with password and keyboard-interactive login disabled. The Orca servers bind on the machine but the firewall only trusts `tailscale0`, and they advertise the Tailscale IP as their pairing address. Orca's own docs warn against exposing its port publicly.
- **Pairing links** grant full access to an Orca server. They live in a per-user log readable only by that user. Orca issues a separate, revocable grant to each paired client; see [Remote Orca Servers](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/remote-servers.mdx#access-and-security).
- **Users** have no sudo. Workers run as their context user, so a misbehaving agent cannot change the system or read the other context's files.
- **Claude workers** in `work` run in Claude Code's `auto` permission mode (classifier-reviewed) instead of bypass mode, set by `homes/work/config/claude-permission-mode`.
- **Pi workers** in `personal` are pinned to the `openai-codex` provider by `config/pi-account`, so they cannot fall back to a paid API key signed in on the same machine.
- **Secrets.** The repo holds no secrets. The Tailscale key lives in `/etc/nixos/secrets/` outside the Nix store; all logins are created on the machine.
