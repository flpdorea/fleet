# Architecture

## The pieces

| Piece | Role |
|---|---|
| Orca's `orchestration` and `orca-cli` skills | Installed globally for each context's harness, so an agent can drive Orca or dispatch work to other agents when asked. |
| [Orca](https://github.com/stablyai/orca) | Owns each agent's git worktree and terminal, and its GitHub integration. Runs headless on the VPS (`orca-ide serve`); the Orca app on your Mac or phone is just a client. |
| Pi | Optional alternative harness (`primary = "pi"`). Uses GPT-5.6 models through the ChatGPT subscription (`openai-codex` provider). |
| Claude Code | The harness of both contexts, each with its own account. Uses Claude Opus 5.5 and Fable 5.1. |
| NixOS + this flake | Declares the whole machine and pins every version. |
| Tailscale | Private network between the VPS and your devices. Orca is only reachable through it. |

## How a request flows

```
 Orca app on Mac/phone ──tailnet──▶ orca-serve-personal (port 6768, user personal)
                                      ├─ worktree + terminal ─▶ claude agent  (Opus/Fable)
                                      ├─ worktree + terminal ─▶ claude agent
                                      └─ ...
```

The `work` context is the same picture with the `work` user, its own Claude account and port 6769.

1. In the Orca app, you open a context's server, pick a repo and start an agent, choosing its harness, model and effort.
2. The Orca server on the VPS creates a worktree and a terminal and launches the harness in it, as that context's user.
3. The agent works, pushes and opens pull requests with that context's GitHub login; Orca shows their status.
4. The app shows every agent's terminal live, and the agents keep running when it is closed.

SSH is only for setup and maintenance: `fleet login`, `fleet pair`, `fleet status` and, as root, `fleet rebuild`.

## Why one Linux user per context

Orca's documentation is explicit: remote sessions use the **server's** `PATH`, home directory and credentials. Workers inherit the Orca server's environment, not the environment of the shell that asked for them.

So per-context separation through environment variables (a different `GH_CONFIG_DIR`, `CLAUDE_CONFIG_DIR` or git identity per shell) would never reach the agents. Instead, each context is a separate Linux user running its own Orca server:

| Isolated per user | Where |
|---|---|
| GitHub account | `~/.config/gh` |
| Git identity | `~/.gitconfig` |
| Claude or Pi login | `~/.claude`, `~/.pi/agent` |
| Global harness config and skills | `~/.claude`, `~/.pi/agent` |
| Orca projects, worktrees, terminals | that user's Orca server |

No environment juggling, and a mistake in one context cannot touch the other's credentials.

## What runs on the machine

Per context (`<ctx>` is `personal` or `work`):

| Unit | Type | Does |
|---|---|---|
| `fleet-setup-<ctx>` | oneshot, as the user | Installs Orca's `orca-cli` and `orchestration` skills globally for the context's harness, and removes what firstmate left on older installs (its clone, `no-mistakes`, `treehouse`, the `*-axi` tools and their hooks). Reruns when the repo or Orca changes. |
| `orca-serve-<ctx>` | long-running, as the user | Waits for the Tailscale IP, then runs `orca-ide serve --port <port> --pairing-address <tailscale ip>`. Logs to `/var/log/fleet/orca-<ctx>.log`. Not restarted by rebuilds. |
| `docker` (user unit) | long-running, in the user's systemd manager | The context's rootless Docker daemon, on `/run/user/<uid>/docker.sock`. Lingering starts it at boot; `orca-serve-<ctx>` points agents at it with `DOCKER_HOST`. |

Machine-wide: `sshd`, `tailscaled`, the firewall, `nix-ld`, weekly Nix garbage collection, and (first boot only) `fleet-bootstrap`.

## Where things live

| Path | Contents | Source |
|---|---|---|
| `/etc/nixos/flake.nix` | The machine's flake. Pulls this repo as the `fleet` input. | Generated by `install.sh` |
| `/etc/nixos/configuration.nix` | Disk, boot, network, root's SSH keys | Generated by nixos-infect |
| `/etc/nixos/fleet.nix` | Enabled contexts, SSH keys, Tailscale key path | Generated by `install.sh` |
| `/etc/nixos/secrets/ts-authkey` | Tailscale auth key (mode 600), single-use and spent after the first boot | `install.sh` |
| `/etc/fleet/contexts.json` | Context list read by the `fleet` command | The module |
| `/home/<ctx>/fleet/` | `.context` and `.ready` markers read by `fleet` | `fleet-setup-<ctx>` |
| `/var/log/fleet/orca-<ctx>.log` | Orca server log, including the pairing link (mode 600) | `orca-serve-<ctx>` |

## Version pinning

| What | Pinned by |
|---|---|
| NixOS, system packages | `nixpkgs` in `flake.lock` |
| Orca, Pi, Claude Code | `llm-agents` in `flake.lock` |
| nixos-infect | Commit hard-coded in `install.sh` |
| Orca skills | **Not pinned.** `orca skills install` fetches them from the Orca repo. |
| Anthropic's `skill-creator` | `anthropic-skills` in `flake.lock` |
| Lavish's `lavish` skill | `lavish-axi` in `flake.lock`. The `lavish-axi` CLI it runs through `npx` is **not pinned**. |

The machine's own `/etc/nixos/flake.lock` records which commit of this repo it runs. `fleet rebuild` moves it to the latest commit.

## Security model

- **Network.** Only SSH (port 22) is open to the internet, with password and keyboard-interactive login disabled. The Orca servers bind on the machine but the firewall only trusts `tailscale0`, and they advertise the Tailscale IP as their pairing address. Orca's own docs warn against exposing its port publicly.
- **Tailnet.** The VPS joins as `tag:fleet`. `tailscale/policy.hujson` only lets your own devices (`autogroup:member`) open connections, so an agent that goes wrong on the VPS cannot reach your laptop or phone through the tailnet.
- **Pairing links** grant full access to an Orca server. They live in a per-user log readable only by that user. Orca issues a separate, revocable grant to each paired client; see [Remote Orca Servers](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/remote-servers.mdx#access-and-security).
- **Users** have no sudo. Workers run as their context user, so a misbehaving agent cannot change the system or read the other context's files.
- **Containers.** Docker runs rootless, one daemon per context user, so a container has no more rights than its user. Nobody is in a `docker` group: access to a rootful daemon amounts to root. Ports a container publishes are ordinary sockets of the user, so the firewall still keeps them off the internet.
- **Secrets.** The repo holds no secrets. The Tailscale key lives in `/etc/nixos/secrets/` outside the Nix store; all logins are created on the machine.
